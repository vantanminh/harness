## Findings

### SEC-df6bdc686ef2b589-001 — Installer does not enforce publisher authenticity

- **Status:** `confirmed`
- **Severity:** `low`
- **Confidence:** `high`
- **Location:** `install/linux.sh:238-243`, `install/macos.sh:238-243`, `install/windows.ps1:254-263`; `.github/workflows/release.yml:271-288`
- **Preconditions:** An attacker controls the GitHub release account/workflow, or a consumer's TLS/trust path is compromised. The attacker supplies both a binary and a matching `SHA256SUMS` row.
- **Path:** installer downloads binary and checksum from the same release tag → verifies SHA-256 → executes; optional `SHA256SUMS.sig`/GitHub attestation is not verified by the installer.
- **Impact:** A release-account compromise can publish a malicious binary with a matching checksum. The checksum protects transfer integrity, not build provenance or publisher identity.
- **Evidence:** All three installers abort when the manifest is missing or the digest mismatches; release CI emits attestations and signs only when `GPG_PRIVATE_KEY` is configured. Consumer guidance documents manual signature/`gh attestation verify` checks.
- **Fix direction:** Make a trusted Sigstore/GitHub-attestation or pinned maintainer-key verification step mandatory for standalone installers, or make consumers verify the attestation before invoking the installer. Keep SHA-256 as the integrity check.
- **Regression proof:** Existing checksum-mismatch packaging test; add a fixture that rejects an invalid/missing authenticity proof once a verifier is selected.

### SEC-df6bdc686ef2b589-002 — Slow MCP request bodies have no read deadline

- **Status:** `likely`
- **Severity:** `low`
- **Confidence:** `medium`
- **Location:** `src/app/mcp.rs:699-701` (`mcp_loop`); `tiny_http 0.12` accepted-socket handling
- **Preconditions:** A client can reach a non-loopback MCP bind and sends a request body (including a declared `Content-Length`) one byte at a time.
- **Path:** tiny-http returns a request → the MCP loop calls `request.as_reader().take(...).read_to_string(...)` → the per-connection read can wait indefinitely while a task-pool thread and socket remain occupied. The byte cap limits memory, not elapsed time.
- **Impact:** Enough slow clients can consume worker threads/file descriptors and reduce availability. The default loopback bind limits the practical exposure; a reverse proxy can provide a timeout.
- **Evidence:** Static inspection confirms no public tiny-http 0.12 API for an accepted-socket read deadline. Body/header limits, rate limits, and response bounds pass tests, but no slow-client runtime probe was attempted in this environment.
- **Fix direction:** Terminate public traffic at a reverse proxy with strict header/body read timeouts, or replace/configure the HTTP server with per-connection deadlines and add a slow-client regression probe.
- **Regression proof:** Add a local socket test that drips a bounded body and verifies the server closes/responds within the configured deadline.

### SEC-df6bdc686ef2b589-003 — Project-authored command execution is bounded and explicit

- **Status:** `not-a-finding`
- **Severity:** `info`
- **Confidence:** `high`
- **Location:** `src/cli.rs:2298-2475`, `src/app/durable.rs:30-45`, `src/app/mcp.rs:75-94`
- **Evidence:** Missing `--allow-project-command` blocks execution; `verify-all` preflights all commands before running; commands reject NUL/newline/overlong input; output is capped/redacted/truncated; execution times out and terminates process trees where supported; MCP tool discovery has no verify/tool-check execution method. Durable, timeout, output, and tool-check tests pass.
- **Residual risk:** An operator who explicitly approves a repository-authored command grants the local OS user's permissions. This is not a sandbox; use an external sandbox for untrusted repositories.
